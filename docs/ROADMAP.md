# SkillGraph — контекст следующих версий

## Подключение AI-клиентов

Интеграция не должна быть жёстко привязана к Cursor. MCP-сервер остаётся
провайдер-независимым ядром, а установка конкретного клиента оформляется как
отдельный адаптер конфигурации.

Планируемые адаптеры:

- Codex — базовое подключение и write-инструменты реализованы;
- Cursor;
- Claude Desktop и Claude Code;
- VS Code / GitHub Copilot при наличии MCP-поддержки;
- другие локальные и удалённые MCP-клиенты;
- ручная выдача готовой конфигурации для неизвестного клиента.

Интерфейс приложения в будущем должен показывать список клиентов, статус
подключения, путь к их конфигурации и результат тестового вызова
`resolve_task_context`. Добавление нового клиента не должно менять формат
реестра, графа или скиллов.

## Удалённые репозитории

В 0.8 доступны два read-адаптера: GitHub/GitLab и произвольный HTTPS-сервер,
который возвращает реестр SkillGraph, массив скиллов, `items` с Markdown в
поле `content` либо одиночный Markdown. Репозиторий не клонируется, а токены
используются только для одного запроса и не записываются в реестр. Подробности
находятся в `REMOTE-SOURCES.md`.

Следующие шаги для удалённых источников:

1. предварительный просмотр изменений до применения;
2. явная стратегия конфликтов: оставить локальный, принять удалённый или
   создать новую версию;
3. ETag/commit-based обновление только изменившихся документов;
4. безопасное хранение учётных данных через Windows Credential Manager;
5. OAuth для GitHub/GitLab и серверов с поддержкой OpenID Connect;
6. push-адаптер только после отдельного разрешения пользователя;
7. MongoDB/CouchDB-адаптеры через тот же контракт источника.

## Агентно-ориентированная среда

Цель — дать каждому агенту собственную роль и набор скиллов, не создавая
копии скиллов и не привязывая ядро к конкретной нейросети. Агент хранит ссылки
на общий реестр, а SkillGraph строит для него разрешённый контекст задачи.

### Реализовано в 0.9

- коллекция `agents` в `registry-v2` с безопасной миграцией существующего реестра;
- профиль агента: имя, роль, провайдер, цвет, статус, описание и разрешения;
- корневые скиллы агента как ссылки на общий реестр в режиме `follow-registry`;
- ручное назначение скиллов через диалог и drag-and-drop из навигатора;
- назначение агентов проектам без копирования скиллов;
- отдельный раздел «Агенты» с режимами «Профили» и «Маршрут»;
- горизонтальные дорожки проекта от задачи к результату с разрешённой цепочкой каждого агента.

Автоматическая маршрутизация текста задачи, MCP-инструмент
`resolve_agent_context`, handoff и аудит реализованы ниже как продолжение 0.9.

### Реализовано в продолжении 0.9 (пункты 6–10)

- `resolve_agent_context`: объединяет корни проекта и агента, проверяет назначение,
  право чтения и политику доверия к удалённым источникам;
- рекомендательный роутер задач: оценивает роль, ключевые слова, приоритет и
  релевантность скиллов, показывает уверенность и объяснение, но не запускает агента;
- сущность `handoff` и интерфейс передачи задачи, результата, открытых вопросов и
  списка использованных скиллов между назначенными агентами;
- локальные ограничения: права агента, проектная allowlist через назначения и
  блокировка недоверенных удалённых скиллов по умолчанию;
- локальный журнал аудита с агентом, проектом, действием, скиллами, длительностью
  разрешения и размером контекста;
- MCP-инструменты `route_agent_task`, `create_agent_handoff`, `list_agent_audit` и
  `record_agent_outcome`.

### Реализовано в продолжении 0.9 (пункты 11–12)

- единый runtime-контракт для Codex, Cursor, Claude, Copilot, локальных и других
  клиентов без изменения модели агента, проекта или скилла;
- матрица capabilities с read-only по умолчанию и отдельной проверкой разрешений
  агента перед write-операциями;
- экран «Runtime» и MCP-инструмент `list_agent_runtimes` для просмотра адаптеров;
- экран «Оценка» для локального сравнения выполнения задачи с цепочкой SkillGraph
  и без неё по успешности, полезности и длительности;
- MCP-инструменты `record_agent_evaluation` и `list_agent_evaluations`;
- записи оценки не требуют сохранять исходный пользовательский промпт.

Следующий уровень развития: capability-токены для каждого AI-клиента,
подтверждения опасных write-вызовов на стороне клиента, параллельные ветки
handoff и автоматизированный прогон воспроизводимых наборов задач.

### Уточнение runtime и аудита в 1.0

- подключения всех поддерживаемых клиентов получают идентификатор вызывающего
  провайдера через `--client-provider`;
- `agent.provider` проверяется перед `resolve_agent_context` и
  `record_agent_outcome`: Codex не может выполнить профиль Cursor и наоборот;
- Task Manager работает через любой провайдер из собственного профиля и создаёт
  межпровайдерные планы и handoff без привязки к Codex;
- `list_agent_handoffs` служит очередью входящих передач для целевого runtime;
- разрешение контекста целевым runtime автоматически принимает pending-handoff,
  а запись результата автоматически завершает его;
- аудит маршрутизации, контекста, handoff и результата создаётся MCP автоматически
  и хранит назначенный, вызывающий и фактический провайдер;
- подключение MCP не считается запуском внешнего приложения: Cursor выполняет
  задачу только когда сам Cursor обращается к своей очереди и контексту.

### Реализовано: гибридные автономные запуски (версия остаётся 1.0)

- Task Manager любого провайдера создаёт сохраняемый запуск и план зависимых подзадач;
- Codex, Cursor, Claude, Copilot, local и custom регистрируют отдельные runtime-сессии, получают только задачи
  своего провайдера и подтверждают их lease-токеном;
- параллельные read/review-этапы разрешены, а запись в один проект защищена
  единственным project-write lease;
- вкладка «Исполнение» показывает горизонтальный swimlane-граф по агентам,
  зависимости, прогресс, текущий этап и состояние подключённых runtime;
- поддержаны пауза, продолжение, отмена, повтор после ошибки и безопасное
  возвращение задачи в очередь после истечения lease;
- очередь, результаты и артефакты восстанавливаются после перезапуска desktop и
  MCP; проект с незавершённым запуском нельзя удалить;
- desktop и MCP используют общий межпроцессный lock и ревизию реестра, чтобы не
  перезаписывать более свежие изменения друг друга.

Следующий шаг: отдельный worker-loop/команда активации для Codex и Cursor,
настраиваемые политики подтверждения write-задач и управление лимитами очереди
из интерфейса.

### Этап 1. Модель агентов

- добавить коллекцию `agents` в `registry-v2`;
- поля агента: стабильный `id`, отображаемое имя, роль, провайдер, описание,
  статус и список корневых скиллов;
- хранить назначения как ссылки на ID скиллов с режимом `follow-registry`;
- разрешить одному скиллу обслуживать несколько агентов без копирования;
- подготовить миграцию, которая оставляет существующие реестры валидными.

Критерий готовности: агент создаётся и удаляется без изменения скиллов, а
обновление версии скилла автоматически видно всем назначенным агентам.

### Этап 2. Интерфейс рабочих областей агентов

- отдельный раздел «Агенты» в навигаторе;
- карточка агента с ролью, назначенными корневыми скиллами и разрешённой
  цепочкой зависимостей;
- drag-and-drop скилла на агента и между агентами;
- фильтры «доступно агенту», «общее» и «конфликтует»;
- визуальная маркировка узлов графа цветом агента без дублирования узлов;
- массовое назначение и снятие назначений с подтверждением.

Критерий готовности: пользователь понимает, какие инструкции получит каждый
агент, до подключения AI-клиента.

### Этап 3. Разрешение агентного контекста

- новый MCP-инструмент `resolve_agent_context`;
- вход: `agentId`, задача, проект и активные файлы;
- порядок: скиллы проекта → скиллы агента → зависимости → рекомендации;
- обнаружение конфликтующих правил, циклов и недоступных версий;
- лимит контекста и краткие summaries для цепочек, которые не помещаются;
- результат должен содержать `requiredOrder`, причины выбора и полный текст
  только действительно нужных скиллов.

Критерий готовности: одинаковый запрос для разных агентов возвращает разные,
объяснимые и воспроизводимые цепочки.

### Этап 4. Маршрутизация задач

- правила соответствия задачи агенту по тегам, роли и графу скиллов;
- режим рекомендации без автоматического запуска;
- оценка уверенности и объяснение выбора агента;
- ручное переопределение пользователем;
- fallback-агент и запрет маршрутизации при нерешённом конфликте.

Критерий готовности: SkillGraph предлагает исполнителя, но не запускает агента
и не передаёт данные без явной настройки пользователя.

### Этап 5. Совместная работа и передача контекста

- сущность `handoff`: исходный агент, целевой агент, задача, результат,
  открытые вопросы и использованные скиллы;
- граф последовательных и параллельных этапов;
- защита от циклической передачи задач;
- общий журнал решений и ссылок на артефакты;
- повторное продолжение задачи другим провайдером без копирования реестра.

Критерий готовности: другой агент продолжает работу, видя только разрешённый
контекст, проверяемую историю и актуальные версии скиллов.

### Этап 6. Разрешения и безопасность

- отдельные права агента на чтение, создание, изменение, связи и удаление;
- read-only по умолчанию для удалённых реестров;
- подтверждение опасных MCP-инструментов на стороне AI-клиента;
- allowlist проектов, источников и типов данных для каждого агента;
- аудит всех изменений с указанием агента, клиента и источника;
- защита от инструкций, полученных из недоверенного удалённого скилла.

Критерий готовности: назначение скилла не расширяет права агента автоматически.

### Этап 7. Наблюдаемость и оценка качества

- журнал: какой агент, проект и набор скиллов использовались;
- длительность разрешения контекста и размер переданных инструкций;
- успешность задачи и ручная оценка полезности скилла;
- обнаружение неиспользуемых, дублирующих и конфликтующих скиллов;
- сравнение результатов с цепочкой и без неё без сохранения чувствительных
  пользовательских запросов по умолчанию.

Критерий готовности: пользователь может понять, почему агент получил скилл и
помог ли этот скилл результату.

### Этап 8. Провайдер-независимый runtime

- единый контракт адаптера агента поверх MCP;
- Codex и Cursor как первые реализации;
- Claude, Copilot и локальные модели как независимые адаптеры;
- проверка capabilities перед выдачей write-инструментов;
- удалённый runtime только после появления аутентификации, шифрования и
  явного управления сроком сессии.

Критерий готовности: добавление нового AI-клиента не требует менять формат
агентов, скиллов, проектов или графа.
